# 기여 및 커밋 규칙

계산기 프로젝트의 변경 이력을 쉽게 이해할 수 있도록 다음 규칙을 따릅니다.

## 커밋 메시지 형식

```text
타입: 변경 내용
```

- 타입은 아래 표의 영문 소문자를 사용합니다.
- 콜론(`:`) 뒤에는 공백을 한 칸 넣습니다.
- 변경 내용은 한국어로 간결하고 구체적으로 작성합니다.
- 제목 끝에 마침표를 붙이지 않습니다.
- 변경 이유나 주의 사항이 필요하면 제목 다음에 빈 줄을 넣고 본문에 작성합니다.

## 커밋 타입

| 타입 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 기능 추가 | `feat: 덧셈 함수 구현` |
| `fix` | 오류 수정 | `fix: 0으로 나누는 경우 예외 처리` |
| `docs` | 문서 작성 및 수정 | `docs: 커밋 메시지 규칙 작성` |
| `refactor` | 동작을 유지하는 코드 개선 | `refactor: 연산 선택 로직 분리` |
| `test` | 테스트 추가 및 수정 | `test: 뺄셈 함수 테스트 추가` |
| `chore` | 설정 등 기타 작업 | `chore: 파이썬 캐시 gitignore 등록` |

## 커밋 작성 원칙

1. 하나의 커밋에는 하나의 목적을 담습니다. 관련 없는 코드 변경과 문서 수정은 나누어 커밋합니다.
2. `수정`, `완료`, `업데이트`처럼 변경 내용을 알 수 없는 메시지는 피합니다.
3. 코드 변경 시 관련 기능을 실행하거나 테스트하여 정상 동작을 확인합니다.
4. 커밋에 포함할 파일을 확인하고 필요한 파일만 스테이징합니다.
5. 비밀번호, API 키, 개인 환경 설정, `__pycache__/` 등의 캐시 파일은 커밋하지 않습니다.

### 메시지 예시

```text
feat: 곱셈 함수 구현
```

설명이 필요한 경우:

```text
fix: 0으로 나누는 경우 예외 처리

제수가 0이면 ValueError를 발생시키도록 변경한다.
호출하는 코드에서 예외를 처리할 수 있도록 한다.
```

## 커밋 절차

프로젝트 루트에서 다음 순서로 진행합니다. 아래는 이 문서만 커밋하는 예시입니다.

```bash
# 변경 파일과 내용을 확인합니다.
git status
git diff

# 커밋할 파일을 선택합니다.
git add docs/CONTRIBUTING.md

# 실제 커밋에 포함될 내용을 확인합니다.
git diff --staged

# 규칙에 맞는 메시지로 커밋합니다.
git commit -m "docs: 커밋 메시지 규칙 작성"
```

## 커밋 전 체크리스트

- [ ] 커밋이 하나의 명확한 목적을 담고 있나요?
- [ ] 메시지가 `타입: 변경 내용` 형식을 따르나요?
- [ ] 변경한 코드의 동작을 확인했나요? (문서만 변경한 경우 제외)
- [ ] 스테이징된 변경에 불필요한 파일이나 민감한 정보가 없나요?
- [ ] 관련 문서에 수정이 필요하다면 반영했나요?

# 코드 리뷰 규칙

## 기능 통일성

- 기존 기능의 동작 방식과 새로 추가된 기능의 동작 방식이 일관적인지 확인한다.
- 동일하거나 유사한 기능이 중복 구현되지 않았는지 확인한다.
- 기존 기능의 입력/출력 형식과 새 기능의 형식이 일관적인지 확인한다.
- 하나의 함수나 클래스가 너무 많은 역할을 담당하지 않는지 확인한다.
- 기존 기능을 수정한 경우 다른 기능에 영향을 주지 않는지 확인한다.

## 이름 통일성

- 변수, 함수, 클래스 이름이 프로젝트의 기존 네이밍 규칙과 일치하는지 확인한다.
- 같은 의미의 값에 서로 다른 이름을 사용하지 않는지 확인한다.
- 의미를 알기 어려운 축약어나 지나치게 짧은 이름 사용을 지양한다.
- 함수 이름은 해당 함수의 역할을 쉽게 이해할 수 있도록 작성한다.

## 위험성

코드 변경으로 인해 예상하지 못한 오류가 발생할 가능성이 있는지 확인한다.

- 기존 기능이 깨질 가능성이 있는지 확인한다.
- 입력값에 따라 예외가 발생할 가능성이 있는지 확인한다.
- None, 빈 값, 잘못된 타입 등 예외 상황을 고려했는지 확인한다.
- 파일 삭제, 데이터 수정 등 복구하기 어려운 작업이 포함되어 있는지 확인한다.
- 필요 이상의 파일이나 코드가 변경되지 않았는지 확인한다.
- 보안상 위험할 수 있는 정보가 포함되지 않았는지 확인한다.

## 유지보수성

- 코드의 목적을 쉽게 이해할 수 있는지 확인한다.
- 지나치게 복잡한 조건문이나 반복문이 없는지 확인한다.
- 동일한 코드가 여러 곳에 중복되어 있지 않은지 확인한다.
- 하나의 함수가 지나치게 길지 않은지 확인한다.
- 수정이 필요한 부분이 여러 파일에 불필요하게 분산되어 있지 않은지 확인한다.
- 필요한 경우 주석이나 문서가 작성되어 있는지 확인한다.

## 리뷰 결과 기준

리뷰어는 다음 세 가지 방식으로 리뷰 결과를 남긴다.

| 구분 | 의미 |
| --- | --- |
| **Approve** | 문제 없이 병합 가능 |
| **Comment** | 참고하거나 개선하면 좋은 사항 |
| **Request changes** | 병합 전에 반드시 수정해야 하는 문제 |

다음과 같은 경우에는 **Request changes**를 사용한다.

- 기존 기능이 정상적으로 동작하지 않게 되는 경우
- 명확한 버그가 존재하는 경우
- 보안상 위험이 있는 경우
- 프로젝트의 핵심 규칙을 위반한 경우
- 유지보수가 매우 어려운 구조가 추가된 경우

단순한 코드 스타일이나 개인 취향 차이는 가능하면 `Comment`로 남긴다.

## 코드 리뷰 체크리스트

- [ ] 기존 기능과 새 기능의 동작 방식이 일관적인가?
- [ ] 동일하거나 유사한 기능이 중복 구현되지 않았는가?
- [ ] 변수, 함수, 클래스 이름이 기존 규칙과 일관적인가?
- [ ] 이름만 보고 역할을 이해할 수 있는가?
- [ ] 기존 기능에 영향을 줄 가능성이 없는가?
- [ ] 예외 상황이나 잘못된 입력이 고려되어 있는가?
- [ ] 보안상 위험한 정보가 포함되어 있지 않은가?
- [ ] 코드가 지나치게 복잡하거나 중복되어 있지 않은가?
- [ ] 다른 팀원이 수정하기 쉬운 구조인가?
- [ ] 불필요한 파일이나 코드가 함께 변경되지 않았는가?
## 충돌 발생 시 기본 대응 흐름

충돌이 발생하면 임의로 강제 푸시하거나 공유 브랜치의 히스토리를 다시 쓰지 않습니다.

1. 충돌 사실과 관련 브랜치를 팀에 공유합니다.
2. 최신 `main`을 받아 현재 작업 브랜치에 반영합니다.
3. 충돌 난 부분을 확인하고 필요한 내용을 합의하여 수정합니다.
4. 수정 후 실행 또는 변경 내용을 확인합니다.
5. 중요한 충돌은 `docs/conflict-resolution.md`에 간단히 기록합니다.

충돌 해결 방식은 상황에 따라 자유롭게 선택하되, 다른 팀원의 작업을 임의로 삭제하지 않습니다
